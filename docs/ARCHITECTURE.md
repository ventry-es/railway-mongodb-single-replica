# Architecture

## The shape of the deployment

One service, one volume, one replica set member:

```
mongodb   volume /data   replica set rs0   member mongodb.railway.internal:27017
```

There is no second service. The three-member template needs an `init` service
to add and reconcile members; with one member there is nothing to reconcile,
so the node configures itself.

Clients reach the node over Railway's private network at its
`*.railway.internal` domain. That domain is also the member's host in the
replica set configuration, which matters: a driver connecting with
`replicaSet=` reads the host from the server and connects to *that*, so it has
to be a name every client can resolve. `mongod` binds with `--bind_ip_all
--ipv6`: private networking is IPv6-native, and environments created before
October 2025 are IPv6-only.

`mongod` runs as PID 1, so Railway's `SIGTERM` reaches it directly and a
redeploy shuts it down cleanly instead of killing it mid-write.

## Booting the node

`mongo/scripts/entrypoint.sh`, in order:

1. **Validate the environment.** Missing or malformed variables stop the boot
   with a message naming the variable, rather than surfacing later as an auth
   error.
2. **Assert persistent storage** (`lib/volume.sh`). `/data` must be a real mount
   point, and must match `RAILWAY_VOLUME_MOUNT_PATH` when Railway provides it.
3. **Prepare directories.** `/data/mongodb` for the database, `/data/state`
   (mode 0700) for everything this template needs to remember. Ownership is
   fixed only on files that do not already belong to `mongodb`, so this does not
   become a full pass over a large volume on every boot.

   The database deliberately does *not* live in the conventional `/data/db`.
   The official image declares `VOLUME /data/db`, and Docker honours that even
   when `/data` is already mounted: it creates a *second*, anonymous volume over
   `/data/db`, and the database ends up outside the volume that was mounted for
   it. Moving the dbPath one directory across sidesteps that entirely.

   `/data/db` and `/data/configdb` are still created, empty and unused, because
   the official entrypoint runs `find -L /data/configdb /data/db` under `set -e`
   before it starts mongod. **Railway ignores `VOLUME` declarations**, so unlike
   Docker it does not conjure those paths — without them `find` exits non-zero
   and the container restarts before mongod ever runs.

   That difference is worth remembering: `tests/e2e.sh` runs on Docker, so it
   cannot reproduce Railway-only runtime behaviour. A real deployment is still
   the only way to prove a change works there.
4. **Ensure the keyfile** (`lib/keyfile.sh`).
5. **Pin the replica set name** (`lib/replicaset.sh`).
6. **Wait for the node's own name to resolve** (`lib/replicaset.sh`).
7. **Move a renamed member** if the service's name has changed
   (`lib/replicaset.sh`), with a short-lived standalone `mongod`.
8. **Reconcile the root password** (`lib/password.sh`).
9. **Initiate the replica set** if it has never been initiated
   (`lib/replicaset.sh`), in the background.
10. **`exec docker-entrypoint.sh mongod …`**, handing the process over to the
    official image so its first-boot user creation still works.

Steps 8 and 9 run as background tasks because they need a `mongod` that is
already listening. Both wait on `hello()` reporting a replica set member rather
than merely answering: while the data directory is empty, the official
entrypoint runs a *temporary standalone* `mongod` to create the root user, and
acting against that one would configure the wrong server. Step 7 runs in the
foreground and has finished before either task starts, for the same reason.

Neither background task can take the deployment down. They log and give up. A
database that is up with the wrong credentials can be repaired; one that
crash-loops on boot invites someone to delete the volume.

Everything the node remembers between boots lives in `/data/state`:

| File | Written | Purpose |
| --- | --- | --- |
| `keyfile` | first boot | Internal authentication key, generated by the node |
| `root-password` | first boot, then on rotation | The password the database actually answers to |
| `replica-set-name` | first boot | The name the set was created with |
| `member-host` | on initiate, then on a rename | The host the member is registered under |

## The defences

### 1. Never write to ephemeral storage

`railway.json` sets `requiredMountPath: "/data"`, and the entrypoint verifies at
runtime that `/data` is a mount point by comparing its device id with its
parent's. Without a volume the database comes up looking perfectly healthy and
loses everything on the next deploy — the check turns a silent, delayed failure
into an immediate, obvious one.

### 2. The keyfile never comes from the environment

`mongod` will not enable authentication on a replica set without a keyfile,
even one with a single member. In a larger set it is the shared secret members
authenticate to each other with; here nothing outside the node ever uses it.

So there is no `MONGO_KEYFILE` variable. On first boot the node writes 756
random bytes, base64-encoded, to `/data/state/keyfile` and never replaces it.
The usual way a keyfile breaks a deployment — a template variable regenerated
under a running cluster — has nothing to act on.

### 3. The root password is remembered, and drift is rotated

The official image creates the root user only when the data directory is empty.
After that `MONGO_INITDB_ROOT_PASSWORD` is ignored — so a regenerated value
locks every client out of a database that is completely intact. This is the
failure most often mistaken for a wiped deployment.

`/data/state/root-password` records what the database was actually provisioned
with, which makes the cases distinguishable:

- sentinel matches the environment → nothing to do;
- sentinel missing, data directory empty → first boot, record and move on;
- sentinel missing, data present → adopt the environment value and verify it in
  the background, warning if it does not authenticate;
- sentinel differs → rotate.

Rotation is a write, so it waits until the node has elected itself PRIMARY — a
few seconds after `mongod` starts — and then calls `changeUserPassword`. The
environment stays the source of truth, which also means rotating the root
password is just changing the variable and redeploying.

### 4. `rs.initiate()` cannot run twice

Re-initiating a configured replica set throws away its identity. The node only
initiates when `rs.conf()` reports `NotYetInitialized` (code 94) **and**
`local.system.replset` is empty.

The second condition is not belt and braces. A node that has a configuration
but cannot find itself in it — after a rename, or with its DNS not yet
resolving — reports exactly the same `NotYetInitialized`. Running
`rs.initiate()` on such a node does not repair it: on MongoDB 9.0 the command
drops the connection and leaves the node unusable. Only an empty
`system.replset` means the set was never created.

`rs.initiate()` runs from inside the node, over localhost, because with
`--keyFile` authentication is on from the first byte and MongoDB's localhost
exception is the only way to configure a set before a client can authenticate.

### 5. A renamed service keeps its database

The member's host — `mongodb.railway.internal:27017` — is written into the
replica set configuration by `rs.initiate()`, and it is the name `mongod`
looks for when it starts. Rename the service and Railway gives it a new private
domain; the old one stops resolving. The node no longer recognises itself,
reports `NotYetInitialized`, and stays that way. Neither
`rs.reconfig({ force: true })` (`no replset config has been received`) nor
`rs.initiate()` can bring it back from there — both verified on 9.0.

MongoDB's documented procedure for this, "Change Hostnames in a Replica Set",
is to start the node as a standalone, rewrite the host in
`local.system.replset`, and start it again. The entrypoint does exactly that,
before the real `mongod` starts:

- `/data/state/member-host` records the host the member was registered under;
- if it differs from the host the node is about to advertise, a standalone
  `mongod` is started bound to `127.0.0.1` only, without `--replSet` or a
  keyfile, the single member's host is updated, and the standalone is shut down;
- the real `mongod` then starts, finds itself under the new name, and elects
  itself PRIMARY. The replica set keeps its `replicaSetId`, its oplog and its
  data.

The standalone runs only when the name has actually changed, and only on a set
with exactly one member. A set someone has grown by hand is left alone.

Consumers that reference `${{mongodb.MONGO_URL}}` pick up the new domain the
next time they deploy.

### 6. The replica set name is fixed by the first boot

A replica set cannot be renamed either: `mongod` started with a different
`--replSet` than the one in its configuration does not recognise itself, with
the same symptoms as a rename. `/data/state/replica-set-name` records the name
from the first boot, and `mongod` is always started with that one. If
`MONGO_REPLICA_SET_NAME` later disagrees, the node keeps serving under the
original name and logs why — the database stays up, and only clients that use
the new name are affected.

### 7. `mongod` never starts before its own name resolves

`mongod` works out which configured member it is by resolving the hosts in its
configuration as it starts. If its own name does not resolve at that moment it
comes up without a valid configuration, and it does not look again once the
name starts resolving. In a larger set a peer's heartbeat would eventually
prompt it; a single member has no peers. Railway's private DNS can trail a
container's start, so the entrypoint waits for `getent hosts` to answer before
starting `mongod`, and restarts the service if it never does.

### 8. The image is pinned

`mongo:9.0`, never `latest`. A newer major refuses to start on a data directory
written by the previous one, which surfaces as a crash-looping database.
Upgrades follow the documented `featureCompatibilityVersion` procedure.

### 9. Paths are part of the contract

`/data` and `/data/mongodb` are constants in the entrypoint, not variables.
Changing a mount path in a template update makes Railway attach a new, empty
volume and orphan the old one — one of the most common ways a "template update"
appears to delete a database.

## Deliberate omissions

**No failover.** It is one node. That is the trade this template makes, and the
three-member template is the answer when it is the wrong one.

**No healthcheck path.** Railway's healthchecks are HTTP and `mongod` does not
speak HTTP. Adding a sidecar to satisfy the dashboard would mean a second
process in a database container for no operational gain.

**No public networking by default.** No TCP proxy, no domains. Exposing a
database to the internet should be a decision, not a default;
[Operations](OPERATIONS.md) covers it when you need it.

**No `MONGO_KEYFILE`.** See defence 2: a secret nothing outside the node uses
has no business being a variable that can be regenerated.
