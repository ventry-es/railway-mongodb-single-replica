# Changelog

Consumers of this template see these notes when Railway offers them an update,
so breaking changes are called out explicitly.

Two things will never change in a minor release, because either would orphan
the data of every running deployment: the `/data` mount path, and the files
under `/data/state`.

## [Unreleased]

First release, not yet published on Railway.

### Added

- Single-member MongoDB 9.0 replica set that initiates itself on first boot, so
  transactions and change streams work on one node.
- Keyfile generated by the node on first boot and kept on the volume; there is
  no keyfile variable that a template regeneration could change.
- Automatic root password rotation: changing `MONGO_INITDB_ROOT_PASSWORD`
  updates the password in the database instead of locking clients out.
- Renamed services keep their database: the member's host is rewritten before
  `mongod` starts, following MongoDB's documented procedure.
- The replica set name is fixed by the first boot, so a changed
  `MONGO_REPLICA_SET_NAME` cannot leave the node without a PRIMARY.
- `mongod` waits for its own private domain to resolve before starting.
- `rs.initiate()` only runs when no replica set configuration exists at all.
- Startup check that refuses to run `mongod` on ephemeral storage, plus
  `requiredMountPath` in `railway.json`.
- `docker-compose.yml` and `tests/e2e.sh` reproducing each failure mode against
  a real node.

### Fixed

- A redeploy could leave the node in `REMOVED`, with no PRIMARY, when Railway's
  private DNS still pointed the service's domain at the previous container
  as `mongod` started. The node now waits for the name to reach it and
  re-applies its unchanged configuration, then elects itself PRIMARY.
- The replica set check no longer runs while `mongod` is still loading its
  configuration. Running it then reported a healthy node as one that "does not
  recognise itself", with identical hosts on both lines.
- `mongod` now waits, up to `MONGO_DNS_SETTLE_SEC` (60 s), for its private
  domain to resolve to the container's own addresses, so a redeploy no longer
  reaches `REMOVED` in the usual case.
- The recovery above gave up when `mongod` closed connections while
  going `REMOVED` ("connection closed"), leaving the node without a PRIMARY.
  Connection errors during the check are now retried.
